# M8: テスト・クラッシュ実験・性能測定・ドキュメント

## このマイルストーンでやること

仕様どおりに動くことを**自動テスト**
で保証し、性能の基準値とドキュメントを整えて、ライブラリとして完成させます。特に大事なのは、人手で確認しづらい3つ:

- **整合性**（データが化けない）
- **リカバリ**（クラッシュしても壊れない）
- **並行性**（同時アクセスで壊れない）

## なぜ必要か

DB の価値は「データが消えない・壊れない」ことです。普通の使い方では問題が出なくても、クラッシュや同時アクセスの瞬間にバグが潜みます。これらは「わざと壊す／わざとぶつける」テストでしか見つかりません。ここを固めて初めて「人に使ってもらえる
DB」になります。

## 出てくる言葉

| 言葉       | 意味                                           |
|----------|----------------------------------------------|
| 単体テスト    | 1モジュールを単独で確認するテスト。各ファイルの `#[cfg(test)]` に書く。 |
| 結合テスト    | 複数モジュールを通して使うテスト。`tests/` フォルダに書く。           |
| プロパティテスト | ランダム入力を大量に試し「どんな入力でも成り立つ性質」を確認（`proptest`）。  |
| クラッシュ注入  | わざと panic / プロセス kill / ファイル切断をして回復を試すこと。    |
| 参照実装     | 「正解」を出すための愚直で単純な実装。検索結果の答え合わせに使う。            |
| ベンチマーク   | 速度を測ること（`criterion`）。                        |
| パラメータ化   | file 版と `:memory:` 版など、同じテストを設定違いで両方流すこと。    |

## 対象

- `tests/`（結合テスト）、各モジュールの `#[cfg(test)]`、`benches/`（任意）、`README` / doc コメント、`examples/`

## 前提

- M1〜M7 を随時。最終統合は全機能が揃ってから。

## 手順（タスク）

### 1. 単体テスト（各モジュール）

- [ ] format: ヘッダ/フレームのラウンドトリップ、壊れ検出（M1 の受け入れ条件をテスト化）
- [ ] metric/search: 参照実装（愚直な全件ソート）との順位一致、ゼロノルム、境界の `k`
- [ ] index: upsert/delete/スロット再利用の不変条件を proptest で

### 2. 結合テスト（`tests/`）

- [ ] CRUD ラウンドトリップ（file と `:memory:` を**同じテストでパラメータ化**して両方流す）
- [ ] 再 open でライブ集合が一致（put/update/delete を混ぜたシナリオ）
- [ ] compact 前後で get/search が一致、ファイルが縮小、generation が +1
- [ ] エラー系を一通り: dim 不一致 / NaN・Inf / payload 超過 / ReadOnly 書き込み / AlreadyExists / UnsupportedVersion /
  InvalidMagic

### 3. リカバリ / クラッシュ実験

- [ ] torn write: 末尾を任意バイト切ったファイルを、RW open → truncate で回復、RO open → 末尾無視（§5.3）
- [ ] 途中破損 → `Corrupt`
- [ ] compact 中断の2ケース（rename **前** / **後**）を擬似的に作り、次回 open の一貫性を確認（§7）
- [ ] 残存 `.compact` の削除（§5.3）
- [ ] 本物のプロセス kill での耐久試験（`SyncMode::Always`）: 子プロセスで put ループ → kill → 再 open して検証（CI で重ければ
  `#[ignore]` を付けて手動実行）

### 4. 並行性

- [ ] 複数スレッドが `Arc<Db>` で同時 search ＋ 書き込み混在のストレステスト
- [ ] プロセス間ロック: 2ハンドル/2プロセスで `Locked` と `lock_wait` の挙動（§8.1）

### 5. ベンチマーク（任意・criterion）

- [ ] put のスループット（SyncMode 別）
- [ ] search のレイテンシ（件数 N × dimension、k 別）
- [ ] open 時のスキャン時間（件数別）
- [ ] 結果を README にベースラインとして記録（最適化の前後比較用）

### 6. ドキュメント

- [ ] クレートルートの doc（概要・クイックスタート）
- [ ] 公開 API の doc コメント（どんな時にどのエラーが出るか、panic するか、計算量）
- [ ] `examples/`（create → put → search → compact の一連の流れ。`:memory:` 版も）
- [ ] アドバイザリロックの限界、SyncMode 別の耐久性保証を明記

## つまずきポイント / 実装メモ

- file と `:memory:` の違いは、テストの**ハーネス（土台）でパラメータ化**して、同じシナリオを両方に流すと楽（コピペでテストを2倍書かない）。
- クラッシュ注入は「途中で panic / プロセス kill」と「ファイルを物理的に切断」の2系統で補い合う。
- どこから手を付けるか迷ったら、**まず参照実装との比較テスト**（検索）と**ラウンドトリップ**（format）から。バグが一番見つかりやすい。
- 余力があれば CI を linux/macos/windows のマトリクスにして、flock や rename のプラットフォーム差を早めに発見する。
