# M6: compact()（ファイルの作り直しでお掃除）

## このマイルストーンでやること

追記オンリーなので、更新や削除を繰り返すとファイルには**古い版やトゥームストーン（消した印）がゴミとして溜まり続けます**。
`compact()` は、今生きているデータだけを新しいファイルに書き直して、**ファイルを小さくする**操作です。しかも*
*途中でクラッシュしても壊れない**ように作ります。

## なぜ「ただ書き直す」だけじゃダメなのか

もし元ファイルを直接上書きしている最中にクラッシュしたら、新旧どちらでもない壊れたファイルが残ります。そこで使うのが *
*atomic rename（アトミックな名前付け替え）** という OS の性質です。

> 同じディレクトリ内での `rename` は**原子的**：「完全に成功」か「何も起きていない」かのどちらかで、中途半端な状態が存在しない（POSIX
> 保証）。

これを使うと、どの瞬間にクラッシュしても「**元ファイルが無傷** or **新ファイルが完全**」のどちらかになり、必ず一貫した状態に戻れます。

## 安全な手順（図）

```
[元ファイル mydb] ← 触らない（無傷を維持）

1. 隣に一時ファイル "mydb.compact" を作る
2. 新ヘッダを書く（generation を +1）
3. ライブなレコードだけを Put フレームで書く（id ごと最新1件、トゥームストーン除外）
4. 一時ファイルを fsync（確実にディスクへ）
5. rename("mydb.compact" → "mydb")  ← ★ここが原子的な瞬間
6. 親ディレクトリを fsync（rename自体を永続化）
7. メモリ上の index のオフセットを新ファイルに合わせて更新

途中でクラッシュしたら？
  ・5の前で死亡 → "mydb.compact" が残る。次回 open で削除すれば元ファイルで一貫
  ・5の後で死亡 → 新ファイルが採用済み。そのまま一貫
```

## 出てくる言葉

| 言葉                | 意味                                      |
|-------------------|-----------------------------------------|
| compact（コンパクション）  | 不要データを物理的に捨ててファイルを作り直すこと。               |
| atomic rename     | 中断されない名前付け替え。クラッシュ安全の鍵。                 |
| generation（世代番号）  | compact のたびに +1 するヘッダの値。どの世代のファイルか分かる。  |
| 一時ファイル `.compact` | 作り直し中の置き場。残っていたら「前回の compact が途中で死んだ」印。 |
| ディレクトリ fsync      | rename という「ディレクトリの変更」をディスクに確実に焼く操作。     |

## 対象モジュール

- `src/db.rs::compact`、`src/storage/file.rs`（一時ファイル・rename・dir fsync）、`src/storage/memory.rs`（メモリ内再構築）

## 前提

- M4 完了（M2 のファイル操作フックを使う）

## 仕様の要点（SPEC §7, §5.3, §5.1 generation）

- 実行中は排他（書き込み・compact・読み取りをブロック。§8）。
- `:memory:` の場合はファイルを使わず、メモリ構造から旧版/トゥームストーンを除いて作り直す。

## 手順（タスク）

### 1. ファイルバックエンド（`file.rs`）

- [ ] `<db>.compact` のパスを計算（**必ず同じディレクトリ**に。別ファイルシステムだと rename が原子的でなくなる）
- [ ] 一時ファイルを作成（前回の残骸 `.compact` があれば先に削除）
- [ ] 新ヘッダを書く（`header.with_incremented_generation()` で generation +1）
- [ ] ライブ集合を書き出す: `index.iter_live()` の各 id について
    - ベクトルはアリーナから取得、payload は**旧ファイル**から `read_at`
    - Put フレームを encode して一時ファイルに append
- [ ] 一時ファイル fsync → `rename(temp → db)` → ディレクトリ fsync
- [ ] 開いているファイルハンドルを新ファイルに差し替える（新ファイルを RW で開き直す／fd を更新）
- [ ] index のオフセット更新方針を決める（**推奨: 書き出す時に新しい payload_offset を記録しながら index を作り直す**
  。新ファイルを再スキャンするより速い）

### 2. メモリバックエンド（`memory.rs`）

- [ ] 新しい `Vec<u8>` にヘッダ + ライブな Put 列を組み立て、index を作り直す（generation +1）
- [ ] ファイル操作は無いので、rename も fsync も不要

### 3. `db.rs::compact`

- [ ] 排他ロックを取る（M7 の write ロック。M7 前なら単純な可変借用でも可）
- [ ] backend の種別（file / memory）で分岐して上の処理を呼ぶ
- [ ] 完了後、メモリ上に持っているヘッダ情報の `generation` も +1 に合わせる

### 4. open 経路との連携

- [ ] open 時に「残存 `.compact` があれば削除」を組み込む（M4 で済んでいれば確認だけ。§5.3）

---

## 動作確認（受け入れ条件）

- [ ] 更新・削除を大量にした DB を compact すると、**ファイルサイズが縮み**、ライブ集合・`get`・`search` の結果が compact
  前と一致する。
- [ ] compact 後に `generation` が +1 されている。
- [ ] 一時ファイル作成後〜rename 前で中断（テストで rename をスキップ）→ 次回 open で `.compact` が削除され、元ファイルで一貫。
- [ ] rename 後で中断 → 次回 open で新ファイルが採用され一貫。
- [ ] `:memory:` でも compact 後にライブ集合が一致し、旧版が消えている。

## つまずきポイント / 実装メモ

- rename が原子的なのは**同一ディレクトリ内だけ**。一時ファイルを別ディレクトリ/別マウントに置かないこと（最頻出のバグ）。
- Windows ではオープン中ファイルの置き換えに癖がある（`ReplaceFile` 相当、または先に元 fd を閉じる必要）。`std::fs::rename`
  と `fs4` の挙動差を要確認。
- payload のコピーは**ストリーミング**で（全件を一度にメモリ展開しない）。大きい DB でメモリが溢れないように。
- 「rename をわざとスキップして中断を再現する」テスト用フックを仕込んでおくと、クラッシュ安全性の検証がラク（M8 で使う）。
