# M3: メモリ上の索引 + ベクトルのアリーナ

## このマイルストーンでやること

「どの id のベクトルが、どこにあるか」をメモリ上で素早く引ける**索引（インデックス）**を作ります。あわせて、検索を速くするためにベクトルを
**1本の長い配列にまとめて並べる置き場（アリーナ）**も用意します。

ここも M1 と同じく**ファイルには触りません**。スキャン結果（M2が渡してくれる「フレームの列」）を受け取って、メモリ構造を組み立てるだけ。純粋ロジックなのでテストが書きやすいです。

## なぜ必要か

検索のたびにファイルを読み直していたら遅すぎます。そこで EmveDB は、起動時に全フレームを1回スキャンして、*
*今生きているベクトルを全部メモリに載せておきます**。検索はメモリ上のアリーナをぐるっと舐めるだけ。だから速い。この「メモリ上の真実」を作るのがこのマイルストーンです。

## 出てくる言葉

| 言葉           | 意味                                                                  |
|--------------|---------------------------------------------------------------------|
| インデックス（索引）   | `id → そのベクトルの居場所` を引く地図。ここでは `HashMap<u64, Entry>`。                 |
| アリーナ (arena) | 全ベクトルを順番に詰めた1本の `Vec<f32>`。例: dim=3 なら `[a0,a1,a2, b0,b1,b2, ...]`。 |
| スロット (slot)  | アリーナ内でのベクトルの**通し番号**（0,1,2,...）。実際の先頭位置 = `slot * dimension`。       |
| 死んだスロット      | 更新や削除で使われなくなったアリーナの隙間。compact か次回 open で回収。                         |
| free_slots   | 死んだスロットの番号を貯めておくリスト。新規追加時に再利用してメモリ肥大を抑える。                           |
| inv_norm     | `1 / ‖v‖`（ノルムの逆数）。Cosine の計算を速くするために**追加時に1回だけ前計算**しておく値。           |
| トゥームストーン除去   | スキャン中に Delete を見たら、その id をライブ集合から外すこと。                              |

### アリーナのイメージ（dimension = 3 のとき）

```
slot:      0           1           2
arena: [ v0 v1 v2 | w0 w1 w2 | x0 x1 x2 | ... ]
         └ id=A ┘   └ id=B ┘   └ id=C ┘
slot 1 のベクトル = arena[1*3 .. 1*3+3] = arena[3..6]
```

## 対象モジュール

- `src/index.rs`

## 前提

- M1 完了（フレームの種別を知っている必要がある。`Storage` には依存せず、スキャン結果を受け取る形にするのが望ましい）

## 仕様の要点（SPEC §9.1）

- open 時に全フレームをスキャンして `HashMap<u64, Entry>` を作る（同じ id は**最新フレーム勝ち**、トゥームストーンは除去）。
- ベクトルは連続した `f32` アリーナに置く。`Entry` には「アリーナ内のスロット」「ペイロードのファイル内位置と長さ」「Cosine用の前計算ノルム」を持たせる。
- upsert/delete すると古いスロットは「死んだ」状態になり、compact か次回 open で回収される。

## 手順（タスク）

### 1. `Entry`：1件ぶんの居場所メモ

```rust
pub(crate) struct Entry {
    pub slot: u32,          // アリーナ内のベクトル番号（先頭 = slot * dimension）
    pub payload_offset: u64,// ペイロードがファイルのどこにあるか
    pub payload_len: u32,   // ペイロードのバイト数
    pub inv_norm: f32,      // Cosine 用: 1/‖v‖（前計算）
}
```

- [ ] `inv_norm` は Cosine 専用の前計算。L2/Dot では使わない（または別用途）。
    - ノルムが 0 のベクトル（全要素0）は割り算できないので、SPEC §6.1 に従い特別扱い（後の検索で最下位になるようにする）。

### 2. `InMemoryIndex`：索引本体

```rust
pub(crate) struct InMemoryIndex {
    dimension: u32,
    map: HashMap<u64, Entry>,  // id → Entry
    arena: Vec<f32>,           // ベクトル置き場
    free_slots: Vec<u32>,      // 再利用できる死んだスロット
    live: usize,               // 生きている件数
}
```

### 3. 操作メソッド

- [ ] `put(id, vector, payload_offset, payload_len)`:
    1. 入れるスロットを決める: `free_slots` に空きがあればそれを再利用、なければアリーナ末尾に新しく確保
    2. ベクトルをそのスロット位置（`slot*dimension` から `dimension` 個）にコピー
    3. もし同じ id が既にあったら、**古い方のスロットを `free_slots` に戻す**（＝死んだスロット回収）。`live` は増やさない
    4. `inv_norm` を計算して `Entry` を作り、`map` に挿入。新規 id なら `live += 1`
- [ ] `delete(id) -> bool`: `map` から取り除き、そのスロットを `free_slots` へ。`live -= 1`。元々なければ false
- [ ] `get_entry(id) -> Option<&Entry>` / `contains(id) -> bool`
- [ ] `vector_of(slot) -> &[f32]`: アリーナから `&arena[slot*dim .. slot*dim + dim]` を返す（検索ループで使う）
- [ ] `len() -> usize` / `is_empty() -> bool`（= `live`）
- [ ] `iter_live()`: 検索が `(id, &Entry, &[f32])` を走査できるイテレータ

### 4. スキャンからの構築

- [ ] `build_from_frames(dimension, frames)`:
    - スキャン結果を**先頭から順に適用**する。Put なら upsert、Delete なら remove。最後に残ったものがライブ集合
    - 注意: Put のとき `payload_offset` は、そのフレームがファイル内のどこにあるか（M2 のスキャン結果に入っている
      offset）から計算する

> なぜ「順に適用」で正しくなる？ → ファイルは追記オンリーで時系列順。先頭から再生すれば、各 id
> について自然に「最後の操作」が勝つ（last-writer-wins）。

---

## 動作確認（受け入れ条件）

- [ ] 同じ id に複数回 put しても `len()` が増えず、`vector_of` で**最新のベクトル**が取れる。
- [ ] delete した後 `contains` が false になり、空いたスロットが `free_slots` 経由で再利用される。
- [ ] `build_from_frames` に「Put → Put（更新）→ Delete → Put」のような列を渡すと、正しいライブ集合が再構成される。
- [ ] スロットとベクトルの境界がズレない（proptest で「どんな操作列でも `slot*dim` の不変条件が保たれる」を確認）。

## つまずきポイント / 実装メモ

- このモジュールは「ベクトルの真実の保管庫（メモリ側）」。**ペイロードの実体は持たない**（offset だけ覚えて、`get()`
  時に遅延ロード。§9.2）。`:memory:` の場合のペイロード実体はメモリ版 storage が `read_at` で返す。
- `inv_norm` は metric が Cosine の時だけ意味を持つ。**推奨設計**: index は inv_norm
  を常に計算して持っておき、検索側がメトリックに応じて使う／使わないを決める（index がメトリックを知らなくて済む）。
- アリーナの肥大化（死んだスロットの蓄積）は、次回 open か compact でリセットされる。実行中は `free_slots` 再利用で抑える。
- まずは「正しく動く」を優先。スロット再利用の最適化で悩んだら、最初は「常に末尾に足すだけ（free_slots なし）」で動かしてから足してもOK。
