## そもそも EmveDB とは（30秒で）

EmveDB は「**ベクトルを保存して、似たものを探す**」ための小さなデータベースです。

- **ベクトル** = 数値の配列（例: `[0.1, 0.5, -0.2, ...]`）。AI が文章や画像を「数の並び」に変換したもの（＝埋め込み,
  embedding）を指します。意味が近いものほどベクトルが近い場所に来る、という性質があります。
- EmveDB がやること = 「このベクトルに**一番似ているベクトルを上位 k 件ちょうだい**」という検索に答えること。これを*
  *近傍検索 (nearest neighbor search)** と呼びます。
- データは**1つのファイル**に全部入ります。サーバを立てる必要はなく、ライブラリとしてプログラムに組み込んで使います（SQLite
  のベクトル版、というイメージ）。

検索の中身は超シンプルで、**保存してある全ベクトルとクエリの距離を1個ずつ計算して、近い順に並べるだけ**
です（これを「全探索 / ブルートフォース」と言います）。賢い索引（HNSW などの ANN）は v1
では作りません。だから「ベクトル検索」と聞いて身構えなくて大丈夫です。難しさはむしろ「ファイルへの安全な保存」の方にあります。

## 用語ミニ辞典（困ったらここに戻る）

### ベクトル検索まわり

| 言葉              | 意味                                                                     |
|-----------------|------------------------------------------------------------------------|
| ベクトル / 埋め込み     | `f32`（32bit浮動小数）の配列。長さ＝`dimension`。                                    |
| dimension（次元）   | ベクトルの長さ。DB ごとに固定（例: 768）。途中で変えられない。                                    |
| メトリック           | 「似ている度合い」の測り方。`Cosine`（向きの近さ）/ `L2`（直線距離）/ `Dot`（内積）の3種。DB作成時に1つ選んで固定。 |
| ノルム (norm)      | ベクトルの「長さ」。`‖v‖ = √(v0²+v1²+...)`。Cosine で使う。                           |
| 距離 (distance)   | 小さいほど似ている、という生の数値。                                                     |
| スコア (score)     | EmveDB では「**大きいほど似ている**」に統一した数値。並び替えに使う。                               |
| top-k 検索        | 「一番似ている k 件」を返すこと。                                                     |
| ブルートフォース（全探索）   | 全件と距離計算する素朴な方法。v1 はこれ。                                                 |
| ペイロード (payload) | ベクトルに付ける「おまけデータ」（任意のバイト列）。EmveDB は中身を見ない。元テキストやJSONを入れる用。              |

### ファイル / システムまわり

| 言葉                   | 意味                                                              |
|----------------------|-----------------------------------------------------------------|
| 追記オンリー (append-only) | ファイルの**末尾に足すだけ**で、途中を書き換えない方式。速くて壊れにくい。                         |
| フレーム (frame)         | ファイルに1回追記する単位。「Put（追加/更新）」と「Delete（削除）」の2種。                     |
| トゥームストーン (tombstone) | 「この id は消した」という目印の Delete フレーム。墓石の意味。                           |
| ライブ (live)           | 今“生きている”レコード。最新フレームが Put で、まだ Delete されていないもの。                  |
| アリーナ (arena)         | ベクトルを**1本の長い配列にまとめて並べた置き場**。バラバラに持つより検索が速い。                     |
| CRC32C               | データ化けを検出するための**チェックサム（誤り検出符号）**。保存時に計算して一緒に書き、読むとき再計算して一致を確認する。 |
| torn write（途中書き込み）   | 書き込みの最中にクラッシュ／電源断して、末尾が中途半端になった状態。                              |
| fsync                | OS のディスクキャッシュを実ディスクに**確実に書き出す**命令。これをしないとクラッシュで消える可能性がある。       |
| アドバイザリロック (flock)    | 「このファイル使用中」という協調的な札。OSが強制はせず、守る側同士で衝突を防ぐ。                       |
| リトルエンディアン            | 数値をバイト列にする時の並び順。下位バイトが先。Rust の `to_le_bytes()` がこれ。             |
| compact              | 古い版やトゥームストーンを物理的に捨てて、ファイルを作り直して小さくする操作。                         |

## 全体の地図：何をどの順で作るか

```
M0 setup ─┬─> M1 format ─┬─> M2 storage ─┬─> M4 db-core ─┬─> M5 search
          │              │               │               ├─> M6 compact
          │              │               └─> M3 index ────┘
          │              │
          └──────────────┴────────────────> (全体) ──────> M7 concurrency ─> M8 testing
```

読み方:

- 矢印の**上流が終わると下流に着手できる**。例えば `M2 storage` は `M1 format` が終わってから。
- `M3 index` は `M1 format` が終われば `M2` と**並行**で進められる。
- `M7 concurrency`（スレッド安全化）と `M8 testing` は各機能と並走するが、**最終的な仕上げはコア（M4〜M6）完成後**。

| #  | ファイル                                   | ひとことで言うと                                         | これが終わってから着手 |
|----|----------------------------------------|--------------------------------------------------|-------------|
| M0 | [00-setup.md](00-setup.md)             | 土台作り。使うライブラリを決め、空のファイルとエラー型・設定型を用意               | —           |
| M1 | [01-format.md](01-format.md)           | 構造体 ⇄ バイト列の変換（ファイルの“文法”）。まだファイルには触らない            | M0          |
| M2 | [02-storage.md](02-storage.md)         | 実際のファイル読み書き・壊れ検出・ファイルロック・`:memory:`              | M1          |
| M3 | [03-index.md](03-index.md)             | メモリ上の索引（id→場所の地図）とベクトルの置き場（アリーナ）                 | M1          |
| M4 | [04-db-core.md](04-db-core.md)         | M2 と M3 を合体。`open/create` と put/get/delete/flush | M2, M3      |
| M5 | [05-search.md](05-search.md)           | 距離計算と top-k 検索 ← **ベクトル検索の本体**                   | M4          |
| M6 | [06-compact.md](06-compact.md)         | ファイルを作り直して小さくする（クラッシュしても安全に）                     | M4          |
| M7 | [07-concurrency.md](07-concurrency.md) | 複数スレッド/プロセスから安全に使えるようにする                         | M4          |
| M8 | [08-testing.md](08-testing.md)         | テスト・クラッシュ実験・性能測定・ドキュメント                          | M1〜M7       |

**おすすめの進め方**: 迷ったら `M0 → M1 → M3 → M2 → M4 → M5 → M6 → M7 → M8` の一本道で進めるのが一番分かりやすいです（M3
を先にやると、純粋なロジックだけで完結して達成感が得やすい）。

## できあがるモジュール構成（`src/`）

```
src/
  lib.rs            // クレートの説明・公開する型のまとめ（re-export）
  error.rs          // EmveError（エラーの種類）, Result<T>
  metric.rs         // Metric（Cosine/L2/Dot）と距離・スコア計算
  options.rs        // CreateOptions / OpenOptions / OpenMode / SyncMode
  format/
    mod.rs
    header.rs       // 先頭64バイトのヘッダの読み書き + CRC
    frame.rs        // Put/Delete フレームの読み書き + CRC
  storage/
    mod.rs          // Storage トレイト（読み書きの共通インターフェース）
    file.rs         // 本物のファイル版（追記・スキャン・壊れ回復）
    memory.rs       // メモリ版（:memory:）
    lock.rs         // ファイルロック（同時アクセスの調停）
  index.rs          // InMemoryIndex（id→場所の地図）+ ベクトルのアリーナ
  search.rs         // SearchOptions / SearchResult / top-k 抽出
  db.rs             // Db 本体（全APIの入り口）
```

- 外から使う型は `lib.rs` で `pub use ...` してまとめる。
- 内部だけで使う型は基本 `pub(crate)`（クレートの外には出さない）にする。

## 全マイルストーン共通のルール

- 各マイルストーンを終えたら、次の4つを**全部緑（エラー0）**にしてから先へ進む:
    - `cargo build` … コンパイルが通る
    - `cargo test` … テストが通る
    - `cargo clippy -- -D warnings` … 推奨スタイル違反0
    - `cargo fmt --check` … 整形済み
- **純粋ロジック（format / metric / index / top-k）は I/O（ファイル操作）から切り離す**。`&[u8]` や `Vec<f32>`
  だけを相手にすれば、テストが書きやすく、バグも追いやすい。
- ファイル操作とロックは `Storage` トレイト越しに扱い、`:memory:`
  を同じトレイトで通す。こうすると「メモリ版で素早くテスト → ファイル版で本番」が同じコードで回せる。
- 実装に迷ったら、各タスクに書いてある **SPEC §x.x** を開いて元の仕様を確認する（このフォルダは仕様の要約なので、最終的な正解は
  SPEC.md）。
