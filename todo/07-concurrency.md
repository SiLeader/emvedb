# M7: 並行性（複数スレッド／プロセスから安全に使う）

## このマイルストーンでやること

`Db` を**複数のスレッドから同時に安全に使える**ようにします。ルールはシンプル:

- **読み取り（get / search）は何人でも同時OK**
- **書き込み（put / delete / flush / compact）は1人ずつ（直列）**
- 加えて、M2 で作った**プロセス間ファイルロック**との統合を確認する

## なぜ必要か

複数スレッドが同時に index やアリーナを書き換えると、データが壊れたり、片方が読んでいる最中にもう片方が書き換えてクラッシュします。これを防ぐのが
**ロック**です。ただし「常に1人ずつ」にすると遅いので、「読むだけなら同時に大勢OK、書く時だけ独占」という賢い仕組み（`RwLock`
）を使います。

## 出てくる言葉

| 言葉                | 意味                                                      |
|-------------------|---------------------------------------------------------|
| `RwLock`（読み書きロック） | 「読み取りは複数同時、書き込みは排他」を実現するロック。`read()` と `write()` の2種の鍵。 |
| 読み取りロック           | `lock.read()`。同時に何個でも取れる。誰かが write 中なら待つ。               |
| 書き込みロック           | `lock.write()`。1個だけ。誰かが read/write 中なら待つ。               |
| `Send + Sync`     | スレッド間で安全に渡せる/共有できる、というマーカー。`Db` がこれを満たすと複数スレッドで使える。     |
| `Arc<Db>`         | 複数スレッドで1つの `Db` を共有するための参照カウント付きポインタ。                   |
| プロセス内 / プロセス間     | 同じプログラム内のスレッド同士 / 別々のプログラム同士。前者は RwLock、後者は flock で調停。  |

## 対象モジュール

- `src/db.rs`（内部の同期）、`src/storage/lock.rs`（M2 で実装したものの統合確認）

## 前提

- M4 完了（M5/M6 と並行可。最終統合はコア完成後）

## 仕様の要点（SPEC §8）

- プロセス内: `Db: Send + Sync`。`get`/`search` は読み取りロック（同時可）、`put`/`delete`/`flush`/`compact` は書き込みロック（直列）。
  `compact` 中は読み取りもブロック。
- プロセス間: RW=排他ロック、RO=共有ロック。RW を持っている間は RO 不可。`lock_wait` で待つ/即エラー。

## 手順（タスク）

### 1. 内部状態を `RwLock` で守る形にする

- [ ] 設計案: 変わらない情報はロックの外、変わる情報はロックの中に分ける
  ```rust
  pub struct Db {
      meta: DbMeta,            // dimension/metric/mode など不変。ロック不要で読める
      inner: RwLock<DbInner>,  // backend + index など、書き換わる部分
  }
  // DbInner { backend: Box<dyn Storage>, index: InMemoryIndex, ... }
  ```
    - `dimension()` / `metric()` のような「変わらない値を返すだけ」のメソッドは `meta` から返せばロック不要で軽い
- [ ] メソッドごとにロックを使い分ける:
    - `get` / `search` → `inner.read()`
    - `put` / `delete` / `flush` / `compact` → `inner.write()`
- [ ] `compact` が `write()` を取ることで、読み取りも自然にブロックされる（§8.2 の「compact 中は読み取りもブロック」が自動で満たせる）

### 2. `Db: Send + Sync` を保証

- [ ] 内部の `dyn Storage` を `Send` にする（`Box<dyn Storage + Send>` 等）
- [ ] `EmveError` も `Send + Sync`（M0 で満たしてあるはず）
- [ ] `SearchOptions.filter` は `Fn(u64) -> bool + Send + Sync`（SPEC §4 と一致。M5 で定義済み）

> コツ: `Db` のフィールドがすべて `Send + Sync` なら、`Db` も自動的に `Send + Sync` になる。コンパイルエラーが「`Send`
> を満たさない」と言ってきたら、犯人のフィールドを直す。

### 3. 使い方の例を追加

- [ ] `Arc<Db>` を複数スレッドに `clone` して同時に `search` する例を doc コメント or テストに追加

### 4. プロセス間ロックの統合確認（M2 の `lock.rs`）

- [ ] RW で開いている間に、2つ目の RW open / RO open が `Locked` になる（`lock_wait=false`）
- [ ] `lock_wait=true` だと、先に開いたハンドルを Drop した後に取得できる
- [ ] `:memory:` はプロセス間ロック無し（プロセス内 RwLock だけ）

## 動作確認（受け入れ条件）

- [ ] 複数スレッドから `Arc<Db>` で同時に `search` してもデータ競合が起きない（`cargo test`。可能なら `loom`/`shuttle`
  か、単純なストレステストで）。
- [ ] 書き込みと読み取りが混在しても壊れない（index とアリーナの整合性が保たれる）。
- [ ] プロセス間ロックの結合テスト（別プロセス起動 or 同プロセス内で2ハンドル）が SPEC §8.1 の表どおりに振る舞う。

## つまずきポイント / 実装メモ

- 最初は**1個の大きな `RwLock`（粗粒度）で十分**。性能問題が出てから、index と writer を分けるなどの細粒度化を考える（早すぎる最適化を避ける）。
- 書き込み中に読み取りがブロックされる時間は「1件 append するだけ」なので普通は十分短い。長く時間のかかる `compact`
  だけは別途、進捗/中断の要件があれば検討（v1 は単純にブロックでOK）。
- `loom`/`shuttle`（並行バグ検出ツール）を入れるなら dev-dependency + `cfg` ゲートで、本体コードに影響させないこと。
